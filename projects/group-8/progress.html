Phase 2 — backend and frontend

October 18, 2026 (Asia/Dhaka). Branch: group-8/milestone-1.

Implemented shared domain validation, the list/check/create tools, validated storage reads, serialized atomic file writes, and an exclusive lock for competing processes. Added a local HTTP API and responsive equipment shelf, loan form, proposal review, explicit Approve and Cancel actions, rule-code feedback, and existing-loan list.

Checks create only in-memory proposals. The trusted approval handler issues a server-held single-use token bound to the proposal, student, and browser session. Creation revalidates stock, student capacity, and dates inside the write operation. The server binds to loopback; workshop student IDs are self-declared. No dependencies or credentials were added.

Verification: npm.cmd run test:browser -- --screenshots passed in local headless Chrome against temporary inventory. Reviewed desktop and mobile screenshots and checked for horizontal overflow and runtime exceptions. Syntax and HTTP integration checks passed. The browser needed to run outside the execution sandbox because its renderer timed out inside it.

Remaining limitations: no production authentication, loan-return management, MCP server, or chat agent. Proposals expire after ten minutes or on restart. A crash may leave a lock file that requires inspection after all server instances stop.

Next step: validate normal, boundary, and invalid flows with the automated behavior suite.

Phase 5 — UI assistant and configurable model adapter

October 18, 2026 (Asia/Dhaka). Added UI chat with tool activity, session-held follow-up context, proposal review, and unchanged explicit approval. The assistant uses an internal MCP JSON-RPC client, sharing the dispatcher and schemas used by external clients. The model adapter supports configurable compatible chat-completions endpoints, bounded tool calls, provider errors, and server-only credentials.

At the user's request, live model configuration is deferred to an ignored local .env file. Empty settings select explicitly labeled demo mode, a limited local parser rather than an LLM. Partial configuration fails startup. A failed configured model never silently switches to demo mode.

Verification: all 36 automated tests pass, including MCP, multi-turn sensor clarification, model tool-loop fixtures, approval-helper denial, loop limits, and provider error redaction. Headless Chrome passes the UI's normal chat proposal, unclear-sensor question and follow-up, cancellation, and approval; existing milestone 1 approval, availability, desktop, and mobile checks also pass. Tests use isolated data and a fixed clock.
