Phase 2: Build the backend and the frontend

2026-10-18

Done

  • Backend (FastAPI): booking_rules.py with 7 rule checks and suggestions, a JSON store with atomic writes, an in-memory proposal queue (15-minute expiry), and the tools layer.
  • REST API: rooms, bookings by day, availability, proposals, approve and reject. Every refusal is a RuleResult with a rule code.
  • Frontend (Next.js 16): booking form with Check and Propose, a Pending approvals panel that refreshes every 3 seconds, and a day schedule.

Decisions

  • tools.py holds list, check and create plus approve and reject, so the MCP server can reuse the first three and never approve.
  • Approve re-checks every rule under a lock; if the re-check fails, the proposal is discarded.
  • The form warns about bookings over 3 hours but still sends them, so the server's rule code is shown.

Phase 5: Add the agent to the UI

2026-10-18

Done

  • Chat agent (app/agent.py) on Groq openai/gpt-oss-120b through the OpenAI-compatible API. It is an MCP client of /mcp, in-process, marked X-CampusDesk-Client: chat.
  • POST /api/chat returns the reply and the real proposals from the store; the Chat panel shows them with Approve and Reject.
  • 111 pytest tests pass, including the agent loop with a scripted LLM (no network in tests).
  • After code review: each chat turn ends within 25 seconds (fallback reply instead of a proxy error), a refused create_booking cannot be followed by an alternative proposal in the same turn, and the Chat panel sends only recent history.
  • Live check with Groq: case 1 gave one proposal (Lab-3, Thursday 13:00-15:00, 2 hours, source chat); case 4 asked for the time and group size; cases 3 and 5 were refused with MAX_DURATION_EXCEEDED and no proposal.

Decisions

  • Groq retired llama-3.3-70b-versatile; of the models on our key, gpt-oss-120b got the Thursday date right and asked for missing details.
  • Every tool result reaches the model inside <tool_data> tags, and a note cannot close the tag early.
  • At most 6 tool rounds and one create_booking per message, both enforced in code; LLM or MCP failures give a fallback reply instead of an error.
