Phase 2 & 3 — Backend/frontend, and behaviour tests

18 October 2026 · Complete (Basics)

Built server/ (Express API, ES modules) and web/ (Next.js App Router UI). Domain validation lives in one module (server/src/domain/booking.js) used by both check_availability and create_booking, so neither call can skip it. Approval is bound to the exact proposal through a server-issued, single-use, 5-minute token (server/src/data/store.js) — a client-supplied approved: true alone is never sufficient. Persistence writes go through a single in-process lock with an atomic write+rename, so a concurrent conflicting create cannot slip in between the availability check and the write.

Validation: server/tests/ — 21 automated tests (node --test) covering the 180/181-minute boundary, a 5-hour refusal, overlap vs. adjacency, unknown room, malformed timestamps, capacity, group size, approval required/mismatched/stale, direct create_booking calls that skip check_availability (still rechecked and still refused with the specific domain code), and two concurrent conflicting creates (exactly one wins). All 21 pass. Manually verified the running Express server over curl (valid booking end-to-end, overlong refusal with a suggested slot, direct-create-without-approval refusal) and the Next.js dev server rendering the full UI against it. next lint is clean.

Not yet built: the MCP server (Phase 4), UI chat and clarification for ambiguous requests (workshop case 4, Phase 5), prompt evals (Phase 6), and injection guardrail testing across every client (workshop case 5, Phase 7). list_rooms, check_availability, and create_booking are implemented as plain functions in server/src/service.js today, called only from the Express routes; wiring them behind an MCP transport is still open.
