Phase 2 & 3 — Backend/frontend, and behaviour tests

18 October 2026 · Complete (Basics)

Built server/ (Express API, ES modules) and web/ (Next.js App Router UI). Domain validation lives in one module (server/src/domain/booking.js) used by both check_availability and create_booking, so neither call can skip it. Approval is bound to the exact proposal through a server-issued, single-use, 5-minute token (server/src/data/store.js) — a client-supplied approved: true alone is never sufficient. Persistence writes go through a single in-process lock with an atomic write+rename, so a concurrent conflicting create cannot slip in between the availability check and the write.

Validation: server/tests/ — 21 automated tests (node --test) covering the 180/181-minute boundary, a 5-hour refusal, overlap vs. adjacency, unknown room, malformed timestamps, capacity, group size, approval required/mismatched/stale, direct create_booking calls that skip check_availability (still rechecked and still refused with the specific domain code), and two concurrent conflicting creates (exactly one wins). All 21 pass. Manually verified the running Express server over curl (valid booking end-to-end, overlong refusal with a suggested slot, direct-create-without-approval refusal) and the Next.js dev server rendering the full UI against it. next lint is clean.

Not yet built: the MCP server (Phase 4), UI chat and clarification for ambiguous requests (workshop case 4, Phase 5), prompt evals (Phase 6), and injection guardrail testing across every client (workshop case 5, Phase 7). list_rooms, check_availability, and create_booking are implemented as plain functions in server/src/service.js today, called only from the Express routes; wiring them behind an MCP transport is still open.

Requested extension — Student requests and independent staff review

18 October 2026 · Implemented

Added separate student and staff sign-in with generated local workshop accounts, salted password hashes, HTTP-only sessions, logout, and server-owned roles. The student dashboard checks availability, presents an exact preview, sends a pending request, tracks decisions, and allows cancellation while pending. The staff dashboard lists requests and presents the full requester, purpose and slot before approval or rejection; rejection requires a reason.

Every mutation enforces its role and ownership in the service layer. Students cannot approve or reject, staff cannot submit as a student, and nobody can review their own request. Approval revalidates live duration, capacity and availability, and writes the booking and final request status in a single serialized transaction. Requests and review metadata persist across restarts. The original booking endpoint cannot bypass staff approval; role fields and invented principals are refused. Existing user bookings were preserved.

Validation actually run: all 37 backend tests pass, including the original booking invariants and new HTTP authorization, ownership, forged roles, stolen/mismatched previews, rejected/cancelled requests, no self-review, live revalidation, concurrent approvals, expired sessions/previews, sign-in failure limits and logout checks. Preserved the existing public health route and development loopback-port support; verified production CORS restricts requests to WEB_ORIGIN. Tests use isolated temporary data. Fixed the test command's Windows wildcard incompatibility. npm run lint and npm run build pass for the frontend. Restarted both local services; checked HTTP 200 for the frontend, successful student/staff sign-in and room/request reads, credentialed CORS and revoked access after logout. The existing booking file's SHA-256 stayed unchanged during verification; private account files are ignored by Git.

Interactive browser checks were not performed: no browser is available in this session. Local generated accounts are intended for the workshop; production SSO, user administration and distributed sessions are not implemented. MCP, chat, prompt evaluations and wider injection testing remain pending.
